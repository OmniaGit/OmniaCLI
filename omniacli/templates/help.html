1. Links to other OmniaCLI instances

A link lets the users of your OmniaCLI see and operate the servers of another OmniaCLI (a customer's machine, for example) from your own pages. Below, the remote is the instance you want to reach, your instance is the one you log in to.

What a link gives you

  • The remote's live servers on your Dashboard, as <link> › <server>, with their load, state and Start / Stop / Restart buttons. A link that does not answer is shown as an error above the list.
  • The remote's pages under /links/<link>/ on your instance, with a bar that says which instance you are on. Every action runs on the remote and is recorded there as manual: link <its name for you> (<your user>).
  • You act there with the lower of your role on your instance and the link's role on the remote.
  • Only users who log in with a password use links; MCP tokens do not.
  • Draft servers of the remote are not listed: a link shows its active servers only.

Step 1 — on the remote: create the link token (admin)

  1. Open the remote's Users page, section Links.
  2. Name the link after who connects, for example omniasolutions, and choose its role: user (watch, restart, start and stop Odoo), developer (also pull, update, backup, pip) or admin (everything).
  3. Press Create link token and copy the token. It is shown only once; the remote keeps only its hash. If it is lost, revoke the link and create a new one.

Without the web interface, on the remote's shell:

omniacli new-link-token omniasolutions --role developer

It prints the token and a line to add under auth.links of the main configuration (/etc/omniacli/omniacli.yaml for the package); restart OmniaCLI afterwards (sudo systemctl restart omniacli): the main configuration is read at startup only.

Step 2 — on your machine: trust the remote's certificate

Your instance checks the remote's HTTPS certificate. It must name the host of the URL in its subjectAltName: the IP address when the URL uses an IP, the DNS name otherwise.

  • A certificate from a public CA (Let's Encrypt and the like): nothing to do, leave the CA file empty.
  • A self-signed certificate, or one from the customer's own CA: save that certificate (or the CA's) on your machine and give its path as the link's CA file.

To save a self-signed certificate (replace host and port):

openssl s_client -connect 192.0.2.10:8443 </dev/null 2>/dev/null \
  | openssl x509 > /etc/omniacli/192.0.2.10.pem
openssl x509 -in /etc/omniacli/192.0.2.10.pem -noout -subject -ext subjectAltName -fingerprint -sha256

Check the fingerprint against the one read on the remote itself (sudo openssl x509 -in <nginx certificate> -noout -fingerprint -sha256): what openssl s_client downloads is whatever answers on that address. The file must be readable by the user that runs OmniaCLI (omniacli for the package).

Step 3 — on your instance: add the link (admin)

Open the Links page and fill in the last row:

FieldValue
Linka name: letters, digits, . _ -. It becomes part of the URLs (/links/<name>/), so the customer's name is a good choice.
URLthe remote's address, https://host[:port][/path], for example https://192.0.2.10:8443. An http:// URL is accepted but the token travels in clear: use it only through a VPN or an SSH tunnel.
Tokenthe token of step 1.
CA fileempty for a public CA, otherwise the path of step 2.

Press Add link, then Test link: it shows the remote's OmniaCLI version and the role you get there. The links and their tokens are saved in the links file of your instance, readable by its owner only.

When it does not work

What you seeWhy
the other instance refused the tokenwrong or revoked token: create a new one on the remote and paste it in the Token field (an empty Token field keeps the saved one).
cannot connect (… certificate verify failed …)the certificate is not trusted (step 2), or it does not name the host of the URL.
cannot connect / no answer in timeaddress, port, firewall, or the remote is down.
no OmniaCLI with links therethe URL reaches something else: check host, port and path.
"Not available: that OmniaCLI is older"the remote runs an older OmniaCLI: its servers are listed, but not the newer parts of the Dashboard (state, buttons, machine charts, disks). Update it.

Behind nginx, the remote must pass on the request headers Authorization and X-OmniaCLI-*; nginx passes request headers on by default.

Removing a link

On the remote, Revoke it on the Users page: it stops working at once. On your instance, Delete it on the Links page.

2. The MCP server

OmniaCLI serves an MCP endpoint (streamable HTTP) for AI clients such as Claude Code:

{{ base_url }}/mcp

A client authenticates with a bearer token, never with a user's password. Every call is listed in the Access log (Users page, admins), with the token, the address and the tool.

Token roles

RoleThe client may
userread: list_servers, server_status, read_log, list_jobs, get_job, pending_updates, dev_setup
developeralso update_test (git pull, update of the changed modules and restart of a test instance) and backup_test, and download backups
adminalso backup and list_backups of any instance (production too), read_server (a server's whole configuration) and add_draft_server (a new server, always a draft). With an admin token, dev_setup, backup and list_backups also reach the draft servers.

A client sees only the tools of its role. A token saved without a role (before roles existed) is a developer. The role can be changed at any time on the Users page; it applies to the next call. No token makes a draft server live: that is Test & activate on the web interface, by an admin.

Step 1 — create the token (admin)

  1. Open the Users page, section MCP tokens.
  2. Name it after the client, for example dev-laptop, choose its role and press Create MCP token.
  3. Copy the token: a string of about 43 letters, digits, - and _. It is shown only once.

The sha256$… value in the users file is the token's hash, not the token: the token cannot be recovered from it, and a client that sends it is refused. A lost token is revoked and created again.

Without the web interface, on the server's shell:

omniacli new-token dev-laptop --role admin

It prints the token and a line to add under auth.tokens of the main configuration; restart OmniaCLI afterwards.

Step 2 — add the server to the client

In Claude Code, on the machine of the client:

claude mcp add --scope user --transport http omniacli {{ base_url }}/mcp \
  --header "Authorization: Bearer <token>"
  • --scope user makes it available in every project; without it, it is registered for the folder the command runs in only.
  • To replace it: claude mcp remove omniacli (in the same scope), then add it again.
  • Check with claude mcp list, or /mcp inside a session.
  • Over HTTPS with a self-signed certificate, the client must trust that certificate as well (step 2 of the links); how depends on the client.

Downloading a backup

backup, backup_test and list_backups answer with a download path. The zip (database dump and filestore) is an HTTP GET on that path with the same header:

curl -fH "Authorization: Bearer <token>" -o backup.zip \
  {{ base_url }}/backups/<server>/<role>/<file>.zip

Add --cacert <certificate> for a self-signed certificate.

When it does not work

What you seeWhy
HTTP 401, "Server rejected the configured Authorization header"the client sends a wrong token: the hash instead of the token, a part of it, or a revoked one. The Access log shows these calls as Failed login through MCP.
"… needs an MCP token with role …"the token's role is too low for that tool: change it on the Users page.
"… is a draft: not live until Test & activate …"the tool works on active servers only; with an admin token, dev_setup, backup and list_backups reach drafts too.
"… is a draft saved incomplete: …"the draft misses settings: complete it on the Servers page.
404 on /mcpOmniaCLI runs on Python older than 3.10, without the MCP library. The package always installs a Python that has it.

3. Adding a server: the fields and the configurations

The Servers page (admins) lists every server, live or draft, with New server, Edit, Clone (the configuration only: no database, no files), Set to draft and Delete (the configuration only: databases and files are not touched). A server is a name and up to two instances, production and test: tick the ones it has, at least one.

Draft and live

  • Save as draft saves without any check, also incomplete. A draft is not live: it is not on the Dashboard, has no actions and no auto update.
  • Save, test & activate (or Test & activate on the Servers page) runs the checks: config and paths readable, click-odoo scripts in the venv and Odoo importable, the database reachable, every repository on its branch without local changes, the service found, sudo allowed, production and test on separate databases and working copies, the backup folder writable. If they all pass, the server goes live; the dialog lists each check.
  • On a live server, Test & save saves the change only if every check passes, otherwise the server stays as it was; Save as draft takes it offline.
  • A server with a running job cannot be edited or deleted. Every save keeps the previous servers file as .bak.

The server

FieldMeaning
Nameletters, digits, . _ -, starting with a letter or a digit. It is part of the URLs and of the backup folders, for example CUSTOMER_V18.

Each instance

Fill in Odoo config file first and press Reload: OmniaCLI reads the database (db_name, or an exact ^name$ dbfilter), the log file (logfile) and the git repositories that hold the addons_path folders, with their branch and remote. What it cannot find is listed under the fields.

Repositories

ColumnMeaning
Nameunique in the instance. A test repository needs a production repository of the same name: Merge test to production pairs them by name.
Paththe git working copy on this machine.
Remotethe git remote to pull from (default origin).
Branchthe branch the working copy must be on: a pull is git pull --ff-only <remote> <branch>, and it is refused when the working copy is on another branch.

A working copy with uncommitted changes is refused by a pull, except on a test instance without auto update: there someone may be working, so the changes are kept (and git refuses to overwrite them).

The three restart configurations

Restart withWhat OmniaCLI doesNeeds
systemdsystemctl --no-ask-password restart|start|stop <service>; the pages show the unit's state, with Start and Stop.with sudo, a sudoers line per command and service.
init.d/etc/init.d/<service> restart; Restart only, the state is unknown.with sudo, a sudoers line.
processOmniaCLI starts odoo-bin -c <config> itself, in the instance's venv, and stops it with a signal; Odoo outlives a restart of OmniaCLI. It refuses to start when another process already runs with the same config. No service name, no Run as.nothing: it runs as OmniaCLI's user.

The sudoers lines go in /etc/sudoers.d/omniacli (the package installs it with examples, all commented); a failed check prints the exact lines. Examples, with your service names and paths:

omniacli ALL=(root) NOPASSWD: /usr/bin/systemctl --no-ask-password restart odoo-customer-test
omniacli ALL=(root) NOPASSWD: /usr/bin/systemctl --no-ask-password start odoo-customer-test
omniacli ALL=(root) NOPASSWD: /usr/bin/systemctl --no-ask-password stop odoo-customer-test
omniacli ALL=(root) NOPASSWD: /etc/init.d/odoo-customer-test restart
omniacli ALL=(odoo) NOPASSWD:SETENV: /opt/odoo/venvs/odoo18/bin/

The last line is for Run as odoo: it allows the programs of that venv folder, and SETENV passes PYTHONPATH. Check a sudoers file with sudo visudo -cf /etc/sudoers.d/omniacli.

On a development workstation, whose repositories and configs belong to you, the whole service may run as your user: OMNIACLI_USER=<user> in /etc/default/omniacli, then sudo dpkg-reconfigure omniacli. The sudoers lines then name that user.

Typical configurations

  • A customer server with a systemd service per instance: production and test, restart systemd with sudo, Run as the Odoo user, auto update on test (for example every 10 minutes), off on production; production gets the tested commits with Merge test to production, which backs it up first.
  • A development or demo machine: one test instance, restart process, an HTTP port per instance when several run on the same machine; no sudo needed.
  • An old server with init.d scripts: restart init.d; Restart only, no Start and Stop.
  • A test instance someone develops on: auto update off, so a pull keeps their uncommitted changes.
